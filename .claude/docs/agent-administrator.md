# The AI administrator-agent: architecture and plan (revision 2)

Status: direction A+ accepted by the owner on 2026-11-05. **Stage 0, Stage 1A and Stage 1B are implemented** (sections 9, 10, 11): the foundation, a draft path and its evaluation harness, all on a fake model so far. There is no agent that sends or acts yet. This file is saved as `.claude/docs/agent-administrator.md`; `plan.md` links to it.

Evidence levels: **code** (in the repo), **tests** (an automated test covers it; last full run 2026-11-04: 518 passed, 6 skipped, 0 failed), **production** (seen on a live system). Production evidence is thin: in the Meta-review test clinic Instagram messages arrived, a manual reply and an AI price reply went out (owner's video); the owner made one automatic booking in a real Cliniccards on 2026-11-04 and removed the visit by hand. The agent flow described here has run nowhere.

## 1. Conclusion and assumptions

Approach **A+**: keep the current pipeline (classifier → facts by code → one structured model call → checks → code executes), add a stored **dialogue state**, a **decision contract** with one content part and at most one next action, and **funnel events**. No free tool-calling loop, no second agent, no new framework.

Assumptions (not measured; to be measured before they are relied on):
- Latency and cost per reply stay close to today only while one model call per message is kept; the prompt grows (state, approved advantages), so tokens per call rise. Measure with the existing `AiUsage` token counts on the fake-to-real eval before any claim.
- A tool loop is not necessarily 2-4 calls; the count depends on the design. A+ avoids the question in stage 1: facts are fetched by code before the call, actions run after it. A second model call is introduced only if the model must *comment on* data it could not see (see 3.6), and then it is measured.

## 3. Architecture

### 3.1 Who decides what
The model decides the **words** and **which one next action** fits; it names services and approved entries by reference only. Code owns every number, time, price, service list, identity, write, confirmation text, hand-over, medical/diagnosis rules, language, limits and modes.

### 3.2 Decision contract (content and next action are separate)
One JSON per turn:
```
content: { kind: ANSWER | CLARIFY | EXPLAIN | HANDLE_DOUBT,
           reply, after, prices: [refs], advantages: [refs], objection: ref | null }
next:    { action: NONE | OFFER_TIME | ASK_CONSENT | COLLECT_DATA | HAND_OFF | CLOSE,
           service: ref | null, reason: code | null }
```
- `content` is what the client reads; it has no side effects. `next` is what the system does after it. Exactly one `content` and at most one `next.action`.
- An answer may carry a next step ("the price is X; shall I look for a time?" = `content ANSWER` + `next OFFER_TIME`). `NONE` is normal: offering a booking is never required in every reply.
- **BOOK is not in the model's vocabulary.** Booking runs only from the existing code path after the client's explicit "yes" (`onConfirmAnswer`).
- Resolution rules (code, deterministic, logged): `HAND_OFF` overrides everything and drops any offer; `CLOSE` overrides everything except an acknowledgement text; `CLARIFY` + `OFFER_TIME` in one turn is invalid → the question stays, the offer is dropped; a `next.action` whose precondition fails (e.g. `ASK_CONSENT` with no chosen time) is replaced by `NONE` and logged; a price question always gets its answer in `content` first.
- Unparseable or contradictory output → the existing retry; after the retry → hand-over (as today).

### 3.3 Stored state (`ConversationState`: one row per clinic + channel + chat, filtered by `clinicId`)
`owner` (BOT | HUMAN), `salesStage` (NEW, DISCOVERY, OFFERED, CONSENT, BOOKING, HANDED, DECLINED, CLOSED), `serviceId`, `needNote` (code label, no free text), `clarifyCount`, `doubtsHandled` (approved entry ids), `lastDecisionMessageId`, `version`, lease fields (3.7), timestamps. No patient name, phone or message text.
The sales stage is separate from the booking status: booking truth stays in `BookingRequest` / the visit in Cliniccards. `salesStage` moves to BOOKING/CLOSED only from the booking system's success event, never from what the model said.

### 3.4 Intent changes and the administrator
Every turn the model sees state and the last messages and may choose any content and next action; code resets what depends on a change (new service clears the open time offer, as `onSlotChosen` does for stale offers). A refusal sets `DECLINED`; the agent stays silent until the client writes with a new intention. A staff message (author set) or an open HANDOFF request sets `owner=HUMAN`; the agent does not answer until staff give the dialogue back (existing resume action). The time pause stays as a second guard.

### 3.5 Existing patients: status is not identity
Three separate notions replace the single `patientKind`:
- `identity`: LINKED or UNLINKED. LINKED only by an explicit link (Telegram link/shared contact, or staff linking in the inbox). A typed phone never links a chat and never discloses personal data.
- `leadStatus`: NEW, POSSIBLY_EXISTING (a card matches a typed phone), EXISTING_LINKED. It is used for routing and for the administrator's note only.
- Disclosure: personal facts (last visit, next appointment) are read and told only for `identity=LINKED` (as `facts()` does now).
Policy: every client, new or existing, may receive information about services, prices, advantages and may book. A LINKED existing patient books without data collection. A POSSIBLY_EXISTING client continues the booking, but the request goes to the administrator with the note "a card with this phone exists, identity to be confirmed" (the behaviour of `runAuto` today); the bot says nothing about the card. Existing patients are not counted as new leads in funnel events (`leadStatus` is stored on the event). No blanket hand-over of existing patients.

### 3.6 Facts first, then the answer
Order of one turn: (1) code reads state, last messages, approved facts (services with refs and price states, approved entries); (2) one model call returns the decision; (3) code validates content and next action; (4) code executes the action and builds the **final message** = model content + code-built blocks (price lines, the time block with buttons, the confirmation question). If the model asks `OFFER_TIME`, the code reads the real free times after the call (as `decide()` already does) and appends them; the model never sees them, so it may not comment on them ("the earliest is tomorrow" is not allowed in stage 1; its intro stays generic: "let me find a time"). If later the model must comment on windows, a second call receives the windows and the final reply is checked again; that is a measured option, not the plan.

### 3.7 Sequential processing without a long lock
No transaction or row lock is held during a model or external call. Instead a **short lease** on the state row (compare-and-set `updateMany`, lease token + `leaseUntil` = now + 90 s):
1. All messages are saved first (existing `ChatMessage` with the event id). The worker claims the lease; if it is taken, the event is left to the lease holder: the holder, after its turn, checks for newer incoming messages and processes the dialogue again (coalescing); a crashed holder's lease expires and the inbound event's own retry (`CLAIM_MS`) picks it up.
2. The decision records the **snapshot marker**: the id of the last incoming message it saw and the state `version`.
3. **Before sending and before any action** the worker re-checks the right to act: lease still its own, `version` unchanged, no newer incoming message, no staff message after the marker, `owner=BOT`, no open HANDOFF, clinic switches still on (`aiEnabled`, `aiAgentMode`, `sendingEnabled`, plan), pause not active. If any check fails the decision is dropped ("stale", logged) and the newer message's turn answers. The same re-check runs at the start of `runAuto` and right before the write `act()` (the existing four-point gate pattern of `AutoBookingGate`).
4. Writes to Cliniccards keep their own claims (`BookingAttempt`, `autoState`, the lost-reply check): a stale decision cannot create a second visit, and an uncertain result is never repeated blindly.

### 3.8 Draft mode (staff approve before sending)
A draft is a pure computation: no message sent, no request created or changed, no visit, no state transition, and the offered times are **not** recorded as shown to the client. Allowed before approval: a decision log record (codes only, marked `draft`) and the AI usage count. Allowed only after the real action: `salesStage`, `clarifyCount`, `doubtsHandled`, "times offered", `BookingRequest` create/patch, HANDOFF request, and every funnel event. When staff press send, a commit step re-validates (owner, no newer incoming message, the offered times still free; otherwise the time block is re-read) and then applies the state and emits the events from the **actual send**. A draft that went stale is shown as such, not sent.

### 3.9 Funnel events (stage 1)
Table `FunnelEvent`: `clinicId`, `conversationId`, `kind` (INQUIRY, TIME_OFFERED, CLIENT_CONFIRMED, BOOKED, HANDED_OFF, DECLINED), `refKey`, `reason` code, `source` (AUTO | ADMIN), `leadStatus`, `occurredAt`. Unique `(clinicId, conversationId, kind, refKey)` so a repeated webhook or a retry cannot double-count. No message text. Emitted at the real action only: INQUIRY at the first incoming message of a conversation; TIME_OFFERED when the message with times is actually sent (refKey = outgoing message id); CLIENT_CONFIRMED when the explicit yes is processed; BOOKED on `finishAuto` success or `confirmByAdmin`; HANDED_OFF when the request is created; DECLINED when `CLOSE` is applied. A visit fact (VISITED) is added only where a reliable source exists: a visit with a known `externalVisitId` (made by the bot) synced back with status VISITED; manual confirmations without a matching visit are not counted. No UI in stage 1.

### 3.10 Per-clinic content (stage 2)
`ADVANTAGE` and `OBJECTION` KB kinds with the existing approval and `reviewedAt` flow, trilingual; clinic tone (warm, neutral, concise). Only approved, non-stale entries reach the prompt, by reference.

## 4. Do the existing validators cover the stated limits?
| Limit | Covered today | Gap |
|---|---|---|
| Invented sums | `CURRENCY` regex on the free text; sums written by code from the price list (`composePriceReply`) | Percent discounts ("-20%"), "free", "акція" without a currency word are not caught on the output |
| Discounts, instalments | Client messages about them are handed over on input (`incomingHandoff` topics) | Nothing on the output side |
| Times | `timesOutsideWindows` checks only `HH:MM` | "завтра", "о третій", dates, weekdays, "ввечері" are not checked |
| Dosage, medicines, diagnosis, instructions | `BAD_REPLY` (short word list) + input classifier | A list, not a guarantee; does not catch every treatment advice |
| Invented advantages, results of treatment, guarantees | **Not covered** by any validator | New output check (lexicon of promises: guarantee, 100%, painless, best, results; percent and "free") as a *blocklist of risk words*, not proof; advantages move into approved entries named by reference and rendered by code, so free text carries none by contract; in draft mode staff see everything; the real-model eval includes a judge check; the residual risk is stated to the owner |
| Language | Language check on the first try | — |

The price and time checks must not be described as protection against invented advantages, discounts or promises of results.

This is the foundation, not the agent. Nothing in the running bot reads the new state or the contract; no prompt, model call or reply text changed.

**Added**
- Migration `20261105100000_funnel_events_foundation` (applied to test databases only): `Clinic.funnelEventsEnabled` and `Clinic.aiAgentMode` (both default false), tables `ConversationState` and `FunnelEvent`.
- `funnelEventsEnabled` is the ONLY switch of the collection. `aiAgentMode` is reserved and nothing reads it; turning it on does not start any collection. Both are set per clinic by the service owner (`PATCH /platform/clinics/:id`, logged in the clinic's audit log); there is no screen for them yet. With the collection flag off nothing is written: neither events nor the conversation row.

**What each event means, and where it is written**
| Event | Written when | Key | Not written for |
|---|---|---|---|
| INQUIRY | the first real incoming message of a chat that the collection sees (`IntakeService.handle`, Telegram text), whatever the reply mode | `first` | draft generation, repeats |
| TIME_OFFERED | a message carrying slot buttons was SENT SUCCESSFULLY (`AutoReplyService`, `BookingFlowService.say`) | incoming message answered + the offered times | a draft; a send that failed or whose outcome is unknown (a send that throws is never recorded) |
| CLIENT_CONFIRMED | the client's yes to ONE concrete time: only the first yes that passes the claim in `onConfirmAnswer` | `requestId:slotTime` | a repeated "yes" or button; a "yes" with nothing waiting; the request mode has no such question, so none is written there |
| BOOKED | a visit was created FOR the request: `BookingService.book` with a `requestId` finished (the `BookingAttempt` that made it carries the request id and the visit id). `source` AUTO for the bot, ADMIN for staff | request id | a failed or unknown write; any visit that was merely found |
| HANDED_OFF | a request for a person really exists: a hand-over, reschedule, cancellation, a booking request passed to the administrator, an automatic booking that could not be done | request id | a booking request still being collected; a draft |
| DECLINED | reserved: no existing action produces it yet (arrives with the agent's `CLOSE`) | | |

**`confirmByAdmin` and BOOKED.** `confirmByAdmin` stores the administrator's statement and looks for a visit of that patient on that day and time. That match proves nothing about THIS request: a visit made by hand, or for another reason, at the same moment looks identical. So `confirmByAdmin` writes **no** BOOKED event, with or without a found visit (it still saves the administrator's words, links the found visit on the request and sends the confirmation, as before). BOOKED comes only from `BookingService.book`, where the visit is created for the request and the link request id → attempt → visit id exists. A visit an administrator enters by hand in Cliniccards (LANKA writes nothing there) therefore does not appear as a booking in this funnel until a reliable link exists (for example the staff choosing the found visit explicitly, a later step).

**One conversation = one permanent chat** (clinic + channel + chat), not an episode of booking. **INQUIRY is the first counted contact of a permanent chat after the collection was switched on for the clinic.** It is NOT a new client, NOT a separate enquiry and NOT a new patient: a patient who has been coming for years counts as an INQUIRY at the first message after the switch; the same chat writing again a month later, or after a finished booking, is not a new INQUIRY; chats that already existed are counted at their next message, so the number rises on the day of the switch. `leadStatus` (EXISTING_LINKED or UNKNOWN) does not make INQUIRY a count of new clients either. Therefore a report must not show BOOKED / INQUIRY as "conversion of new clients"; at most "chats that wrote since <date> and booked". Counting episodes (a new enquiry after a long silence) is a separate decision.

**Guarantee of the events.** An event is written next to the action, outside its transaction, in a separate step. It is **not guaranteed**: a crash between the action and the event, or a failed write (only logged), loses that event; a lost event is possible, an invented one is not (success events are written only after the success is known). A repeated run of the same action is deduplicated by a stable key: request id (BOOKED, HANDED_OFF), request id + slot time (CLIENT_CONFIRMED), `first` (INQUIRY), the answered incoming message + the offered times (TIME_OFFERED, so a handler run again after a crash between the send and the save is the same offer). Not built, on purpose: an outbox for events or writing them inside the action's transaction; that is a larger change and is left for when the numbers are used for decisions.

**Other facts**
- `leadStatus` is `EXISTING_LINKED` when the chat is tied to a card, otherwise `UNKNOWN`. `POSSIBLY_EXISTING` is not computed in this stage.
- Visit facts (VISITED) are not recorded: a reliable source (a synced visit with the known `externalVisitId` of a bot or staff booking and status VISITED) is a later step.
- Retention of events is an open decision before any production pilot; the tables have no purge yet and nothing here treats an indefinite period as agreed. Local development is not blocked by it.
- Nothing was run against production or the real Cliniccards; no paid model was called.

**Test infrastructure found while finishing Stage 0 (the two failures of the first full run)**

## 10. Stage 1A: the agent's draft through the decision contract (2026-11-05, local, fake model only)

**What exists.** A separate path that prepares a reply and a proposed next action, and executes nothing. Nothing was run on a real model, in production or against the real Cliniccards.
- `ai/agent-draft.service.ts` (`AgentDraftService.generate`, `staleness`), `ai/agent-prompt.ts` (its own prompt; the prompt of the working bot is untouched), `ai/guardrails.ts` (new `isPriceQuestion`, `claimProblem`).
- The existing endpoint `POST /conversations/:channel/:chatId/draft` takes the agent path only when the clinic's `aiAgentMode` is on; with it off the working bot's draft and its answer shape are unchanged. The agent draft carries the fields the screen already reads (`reply`, `handoff`, `options`, `reason`) plus `agent`, `status`, `content`, `next`, `handoffSuggestion`, `basis`, `stale`, `modelCalls`.
- **The automatic reply path is NOT connected.** With `aiAgentMode` and `aiAutoReply` both on, an incoming message is still answered by the old path; `generate` is called only from the draft endpoint (a test checks it). Whether an agent-mode clinic should keep the old automatic replies is an open decision; the synthetic test clinic keeps `aiAutoReply` off.

**What a draft contains**
- `reply`: the text (model words + code-written price lines, the notice about a preliminary cost, a line before the offered times).
- `next.proposed` (what the model asked for), `next.action` (what stays after the rules), `next.check { ok, notes, rejected }` (why an action was refused, for example `clarify_with_next_dropped`, `service_missing_in_source`, `no_free_time`).
- `options`: the proposed free times, read, never held or promised.
- `handoffSuggestion`: a hand-over is only SUGGESTED to the administrator (fixed words of the code). **No request is created.**
- `status SAFE_FALLBACK`: after the one repeat the model gave nothing valid (bad JSON, a forbidden action, a sum, a discount word, an invented time, an unknown reference). The text is empty, a hand-over is suggested, nothing else happens.
- `basis` (the last message id and time, the state version and owner, the moment) and `stale`.

**Order of one draft:** read history and the state → counted limit → classifiers BEFORE the model (urgent, health, discounts, complaints → a suggestion to hand over, no model call) → contacts answered by code → facts by code → one model call, one repeat on a refused answer → `resolveDecision` → code-written price lines, risk words, invented times, language → for `OFFER_TIME` the free times are read → staleness check at the end. `BOOK` is not in the model's vocabulary. The model never sees the free times.

**Read-only audit of everything the path calls.** Verified in the code and by a fingerprint test (every table with a `clinicId` plus the clinic row, updates included, must be identical before and after):
| Called | Effect |
|---|---|
| `ChatMessage`, `ConversationState`, `BookingRequest` reads; `KbService.factsFor` | reads |
| `CabinetBookingService.blockReason` → `offers` → `windows` → `fresh` | DB reads, GETs to Cliniccards, an in-memory cache; no DB write |
| `ChatAssistantService.freshOptions` (only when the clinic books by doctors) | reads the free-slot report |
| `AiService.complete` | **the one allowed write**: the model-usage row (`AiUsage`), and the purchased-pack counter only when the monthly allowance is exhausted. It is the cost of a model call, the same as for the working bot's draft |
| NOT called | `DoctorChoiceService.decide/answer/urgent` (its `known()` can refresh doctors in the database), `BookingFlowService`, `AutoReplyService`, `RequestsService`, `BookingService`, anything that sends |

**What a draft does not change:** no message sent, no request or visit created or changed, no hand-over as a real action, no `salesStage`, `owner`, question counters, conversation state row or funnel event (also with the collection flag on).

**Staleness.** A draft is bound to the last message and the state version it was made from. It is stale when, since then, a new incoming message arrived (`new_incoming_message`), a staff member replied (`staff_replied`), another message went out (`new_outgoing_message`), the state changed (`state_changed`) or the owner became a human (`staff_took_over`), or a hand-over request appeared (`handed_to_person`). The check runs at the end of the generation and can be asked again with the basis (`staleness`). Approval and execution of a draft are NOT built; the approval step must refuse a stale draft and re-check the right to act (section 3.7).

**New output check.** `claimProblem` refuses discount, instalment, gift, free, guarantee, "painless", percent and "for ever" words in the model's free text. It is a list of risk words, not a proof against every invented advantage; advantages and objections are not yet in the knowledge base (stage 2), the prompt tells the model to leave them empty, and staff read every draft.

**Checks (all on a fake model whose answers are SCRIPTED by the tests; they prove the rules of the code around the model, not the quality of a real one)** — `test/agent-draft.spec.ts`, 13 tests: a price question with a fitting next step; readiness to book at once; a clarification without an offer in the same turn; a refusal and a request for a person (a suggestion, no request); a change of service; an unknown price (never a number or a zero) and an unknown service; invalid JSON and eight kinds of refused answers (including `BOOK`, sums, a discount, a guarantee, an invented time, a foreign reference) each ending in a safe result with no request created; a new message, a staff reply or a hand-over during generation; clinic isolation (the other clinic's services never reach the prompt, its references are refused, its token cannot read the dialogue); no side effects with automatic sending on; the old path with the switch off; classifiers before the model; the fingerprint check itself detects changes.

**What is still needed before a check on a real model:** (1) the real-model eval set for the agent path (the dialogues of section 6, synthetic data, a cost estimate computed from the current price list; `RUN_AI_EVAL=1`); (2) a judge or review step for invented advantages and promises (the risk words are not enough); (3) a decision on what an agent-mode clinic does with automatic replies; (4) the knowledge entries for advantages and objections (stage 2) and the tone; (5) the approval and execution of a draft with the stale refusal and the right-to-act re-check, and the dialogue lease of 3.7; (6) a screen that shows `next`, the check result and the stale mark to staff (the current screen only shows `reply`, the buttons and the hand-over note); (7) a measured look at tokens per draft (the prompt is larger than the working bot's only in its rules, not in its facts).

## 11. Stage 1B: assembly fixes, drafts-only rule, the evaluation harness (2026-11-05, local; no paid model was run)

**What was changed (agent path)**
1. *Service titles and risk words.* The exact approved title is set aside before the risk-word scan (`claimMatch(text, titles)`); only the title, the text around it is scanned in full. "Безкоштовна перевірка" as the title of a service passes; "лікування у нас безкоштовне" next to it is refused; a text that merely resembles the title ("Безкоштовна перевірка нічого не коштує" for the title "Тестова безкоштовна перевірка") is still refused.
2. *Time: three different things.* The wish of the client, the clinic's hours and a free slot are never mixed. The model's text may contain NO clock time at all (not an echo of the wish, not the hours, not "можемо записати о 19:00"); the old allowance of the clinic's opening and closing times was removed. The code writes the words: the wish as the client said it ("Враховуємо ваше побажання (після 19:00)", "(зранку)", "(ввечері)"), and when no window fits, "На найближчі 7 днів вільних вікон після 19:00 не знайшлося…". The number is the real searched range (`SEARCH_DAYS = 7`, passed to the schedule read), so the text never says that there is no time at all. The clinic's hours are answered by the code when asked. Times offered earlier are still not offered again.
3. *Price.* A hand-over draft keeps the direct answer: the model's references, or, when it gave none for a price question, the one service the question is clearly about (its match score is at least 1.5 times the next one), produce the line ("- … : вартість потрібно уточнити в адміністратора" or the sum) before the offer to hand over. A price line already written in the dialogue is not written again (after "дорого") unless the client asks the price again; a changed service always gets its line. The notice about a preliminary cost follows the lines (only a KNOWN sum).
4. *Text and action.* New refusals with an exact reason for the retry: the inner workings of the product in the client's text ("система покаже суму", "в окремому рядку нижче"), a promise or a statement of a done action in a text whose action is not OFFER_TIME/HAND_OFF ("вже підібрали", "запис оформлено", "передали", "зараз підберемо"; an invitation such as "якщо захочете, можу підказати, як записатися" is allowed), and a service title written with a capital letter in the middle of a sentence in a changed form ("У Тестову консультацію входять…"; a lower-case inflected use is natural and allowed). The prompt says the same. The language check is generic (all titles of the clinic), not a patch for one phrase; it cannot judge grammar, only this class of error.

The whole suite: see the report of this task.

**What this does and does not prove.** The checks were improved against the saved answers and the fake model. This is NOT a confirmed improvement of a real generation: a real model may now be refused more often (every new check can add a retry and a second call) or find new phrasings. Only another paid run can show it; none was made.

**Remaining limits**
- The wish is read by patterns (a clock time after "після/до", the parts of the day "зранку/ввечері/після обіду"); a day of the week, a time in words ("після шостої") and "о 19" without a preposition word are not understood (an evening word is understood).
- The mechanism, promise and changed-title checks are pattern lists, not a language understanding; they refuse and ask again, they never repair a text.
- The service chosen earlier is known to the draft only from the dialogue state; nothing in the product writes it yet (the evaluation simulates it).
- Approval and execution of a draft (and the right-to-act check before an action) are the next stage.

## 15. Stage 2: staff review and approval of a draft (2026-11-05; local, fake transport, no paid call)

**What it does.** With `aiAgentMode` on, "AI draft" in the inbox creates a stored draft (`AgentApprovalService.create`) instead of a throw-away text. Generation still executes nothing. A staff member sees the text the patient would get, the offered windows, a plain-language line about what will be done, the hand-over reason (a fixed code shown as a sentence) and a "stale" mark; the buttons are named by the result: "Send reply", "Send time options", "Hand over to the administrator", plus "Reject" and "Refresh draft". Structured actions cannot be edited: for another text staff use the manual reply, and the draft is then not executed. With `aiAgentMode` off the old draft endpoint and UI are unchanged.

**Storage.** Table `AgentDraft` (migration `20261105120000_agent_draft`): clinic, channel, chat, basis message id and time, `stateVersion`, `basisOwner`, creator, `revision`, `status` (PENDING, APPROVING, SENT, REJECTED, SUPERSEDED, FAILED, UNKNOWN), a server `snapshot` (texts per choice, offered windows, price states, service id, handed-over text), approver, `choice`, `messageId`, `requestId`, `error`. No whole history is copied. Rows older than 30 days are purged by the scheduler; the Meta data-deletion hook deletes the drafts and the state of a deleted chat (covered by a test in `meta-compliance.spec.ts`: drafts, state and funnel events of the chat go, other chats, other channels and other clinics stay; events go through the cascade from the state). The browser sends only `{revision, choice}`; action, price, windows and clinic always come from the server snapshot.

**Endpoints** (OWNER, MANAGER, ADMIN; ANALYST and DOCTOR get 403; a draft of another clinic is 404): `GET /agent-drafts/latest?channel&chatId`, `POST /agent-drafts/:id/approve`, `POST /agent-drafts/:id/reject`. Approval answers 200 with `{ok, outcome: SENT | FAILED | UNKNOWN | REFUSED, code?, reasons?, already?, draft}`.

**Checks before an action.** Staff role, dialogue belongs to the clinic, sending mode (master switch, agent mode, opt-out), `revision` equals the stored one, freshness: a new incoming message or another staff reply after the basis, a changed state version, a changed price state of a service in the snapshot, offered windows re-read from the schedule (`force`, no cache). A stale or changed draft is refused with a code (`stale`, `content_changed`, `options_changed`, `options_unavailable`, `revision_changed`, ...); when only the options changed, a NEW revision with the new windows is stored and shown again first - nothing is sent after the click with different content. `owner=HUMAN` does not block staff approval (the bot's right-to-act check is deliberately not reused); a staff reply that came AFTER the draft makes it stale.

**Actions.** Send reply; send offered windows (not a booking: the patient chooses a time, and no visit is created); explicit hand-over (a HANDOFF request is created or updated BEFORE the text is sent). ASK_CONSENT and COLLECT_DATA are shown as unsupported. Approval by staff is not the patient's consent.

**Double click and failures.** The draft is claimed by a compare-and-set to APPROVING; a second parallel request does not send (answers `in_progress` / `already`). No DB transaction is open while sending. A confirmed error -> FAILED (nothing changed); an ambiguous result (timeout, 5xx, connection lost: `SendError.ambiguous` in the Telegram, Meta and WhatsApp adapters) -> UNKNOWN, never resent blindly, no state, no events; a draft stuck in APPROVING is shown as UNKNOWN. FAILED and UNKNOWN drafts are not re-approvable. No exactly-once guarantee is promised.

**After an unknown result (added after the first review of stage 2).** A new generation does NOT lift the protection. While an earlier approval of the SAME action (the same button) in the same chat is in flight or UNKNOWN, approving that action from any draft is refused with `delivery_unverified` (or `in_progress`); the screen shows "check the chat" with two buttons: "It arrived" (`POST /agent-drafts/:id/resolve {outcome: DELIVERED}`: the draft is closed as sent once, the memory and the events are written, the failed-looking message is cleared) and "Did not arrive: allow sending again" (`NOT_DELIVERED`: status CLEARED, the block ends). Other actions, the manual reply and new drafts are not blocked, so the dialogue is never locked for good; only a person lifts the block. A message of ours with a failed or unknown result no longer hides the patient's last message, so a new draft can be made after a failed or unknown send (before, "nothing to answer" blocked it). Recovery after a stop between the send and the saved result: the proof of a send is ONLY the stored confirmation of the channel for this attempt (`AgentDraft.transportConfirmedAt`, migration `20261105130000_agent_draft_transport_confirmed`, written on its own right after the transport answered, before the message record and the result). A draft left in APPROVING for 2 minutes is completed as SENT (`error: recovered`, memory and event once, the thread record written if it was missing) only when that confirmation exists; a message with the same text in our own table proves nothing, so without the confirmation the draft becomes UNKNOWN and blocks the same action as above. If the write of the confirmation itself is lost, the result is UNKNOWN (the safe side). An ambiguous transport answer stores no confirmation. **Viber.** Its adapter marks every error "not sent" and no partner is bound, so a safe retry cannot be told from an unknown result: approval of agent drafts is refused for it (`channel_not_supported`) and the screen says to write by hand. Allowed: TELEGRAM, INSTAGRAM, MESSENGER, WHATSAPP, WEB (nothing leaves the server).

**State and memory.** Only after a real successful action: sales stage (SEND_TIMES -> OFFERED, HAND_OFF -> HANDED, CLOSE -> DECLINED), the chosen service, `clarifyCount` for a clarifying reply, shown windows. Generation and reject change no state. Funnel events (TIME_OFFERED, HANDED_OFF) only when `funnelEventsEnabled`; the agent memory is written independently of analytics. Approval does not hand the dialogue back to the bot.

**Also changed.** The hard refusal for an inflected service title was removed from the draft path (`inflectedTitle` stays only as a quality flag in the evaluation); reference and fact checks are unchanged.

**Tests.** `test/agent-approval.spec.ts` (15): storage and view without internal references; success with analytics off; events on and a repeated click; two parallel approvals (one send); reply and hand-over; stale (new incoming, other staff reply, regenerate); changed price; changed windows; browser tampering, other clinic, roles; sending off, agent mode off, opt-out, old endpoint; failed vs unknown; reject; owner HUMAN; unsupported action; clarify counter and purge. `agent-draft.spec.ts` (31) is unchanged in meaning (helpers split into service generation and the HTTP path).

**UI check.** Run in a browser against a throw-away API on a test database with a scripted model and fake transport, at 1280 px and 390 px: no horizontal scroll, buttons 40 px on desktop and 44 px at 390 px, text 16 px; uk (ru/en screenshots of the stale state taken). The QA found and fixed one defect (the "result unknown" note was shown twice).

**Limits.** Hand-over via approval keeps one open HANDOFF request per chat; windows are compared as an exact set; Viber is switched off for agent drafts until its errors are classified; the wish parser limits from section 14 remain; no real channel and no real Cliniccards were touched.

**Screenshots** (permanent): `docs/qa-screenshots/agent-approval/` (stale and unknown-result panels at 390 px and 1280 px; `flow/` is the first walk-through).

## 16. Stage 3: from the approved offer to a visit (2026-11-05; local, fake model, fake transport, Cliniccards mock, no paid call)

**Path.** question -> staff-approved reply with the times -> the patient taps a time -> missing data (staff-approved question) -> the patient's consent to the concrete booking (staff-approved question, the patient answers) -> a separate, explicit staff action creates the visit -> the visit is confirmed to the patient. It runs on the existing scenario (`BookingFlowService`) and the existing write (`BookingService.book` with its unique attempt key and reconcile); there is no second booking mechanism.

**Agent mode (`aiAgentMode`) in `BookingFlowService`.** `say()` sends nothing by itself (every scripted message of the scenario is held); `advance`, `complete` and the typed-confirmation branch do not ask, hand over or book; the patient's "yes" no longer reaches `runAuto` (so `aiAutoBooking` has no effect in agent mode); an automatic acknowledgement of `IntakeService` is not sent either. With `aiAgentMode=false` nothing changed (the whole earlier booking suites pass untouched). The write moved into `createVisit` (shared by `runAuto` and the approved path).

**The offer is bound to a message that was really sent.** After a `SEND_TIMES` approval the dialogue state keeps `offerMessageId`, `offeredAt`, `offerService`. A tapped time is accepted only when: that message is the latest sent message with time buttons, the button is on it, it is not older than 24 hours, and the place is still free (read now). An unsent draft, an older offer, another time or a taken place is ignored (no request, nothing sent). A new offer withdraws the choice, the consent and the staged step; a changed time withdraws the consent.

**Steps (code, not the model).** `BookingFlowService.agentPlan` computes the next step from the request: `ASK_DATA` (only the missing fields; a question already asked is not repeated until the patient writes again; after 6 asks a note), `ASK_CONSENT` (the service, date and time, with "yes/no" buttons), `CREATE_VISIT` (only when the consent exists and is still current), or a note without a button (the chosen time is gone, an existing card matches the typed phone, urgent, no length for the service, not possible). Steps are stored as `AgentDraft` rows (`snapshot.step`, `requestId`), staged lazily when the inbox reads the latest draft (no reads of Cliniccards more than once a minute per state), and use the same approval machinery as every draft: revision, compare-and-set claim, stale check (the step is also stale when the request changed), roles, isolation, transport confirmation, unknown-result protection. `POST /agent-drafts/refresh` makes the step again (no model call); `POST /agent-drafts/:id/recheck` checks a visit of unknown result.

**Consent.** `consentKey` = hash(service, time, schedule mode, doctor) at the moment of the question; the patient's yes sets `consentAt` only for a question that was really sent, about what is still current (a changed service or time clears it; a button of an older question does nothing). A "yes" to "shall I find a time?" is not consent: only `stage=CONFIRM` with the consent key counts. Staff approval and the patient's consent are both required and neither replaces the other. The model has no booking action.

**Creating the visit (`bookApproved`).** Requires: agent mode, an open request, the consent for the current key, the write switches (`BookingService.status`), a fresh placement, a card or a new one (an existing card matching the typed phone without a confirmed identity is refused: `identity_needed`; nothing from that card is shown). A new patient gets a card created together with the visit (the summary says so). It then goes through `BookingService.book` with the staff member as the author, so the unique attempt key, the re-check of the place, the read-back and the reconcile apply. A repeated click, two parallel approvals, a repeated "yes" or event do not make a second visit (draft claim, request `autoState`, the attempt key). A taken place after the consent is refused (`slot_unavailable`), nothing is created.

**Unknown result.** A lost answer that the immediate check can settle is recorded as a success once (the earlier behaviour of the automatic mode). When the check also fails the draft is UNKNOWN: nothing is repeated, no "you are booked" is sent, no BOOKED event. "Check the visit in Cliniccards" (`recheck`) reuses the SAME place as the first attempt (the visit that may exist occupies it; a fresh search would pick another cabinet and another attempt key) so `BookingService.book` looks for the visit first. Found: recorded once. Not found and readable: the ordinary guarded attempt.

**Visit and message are separate.** `confirmedAt`/`externalVisitId` are set when the visit exists; the message about it is `noticeStatus` (SENT, FAILED, SKIPPED). A failed message keeps the visit; the existing "retry" sends the message once and never creates a visit (the screen offers it). The text "your booking is confirmed" is built only from the confirmed visit.

**State and events.** `BookingRequest`: `consentKey`, `consentAt`, `consentMessageId`, `cabinetId`, `externalVisitId`, `handledById`, `confirmedBy=ADMIN`; `ConversationState`: `offerMessageId/offeredAt/offerService`, `bookingRequestId`, stage CONSENT (question sent) and CLOSED (visit exists); written with or without the analytics switch. Funnel events (only with `funnelEventsEnabled`): TIME_OFFERED, CLIENT_CONFIRMED (once per question and time), BOOKED (once, by `BookingService.book`).

**UI.** The panel shows the steps with plain names: "Ask the patient for the details", "Ask the patient to confirm the booking", "Create the visit in Cliniccards" (with the booking details and what the patient will receive after the visit exists), "Check the visit in Cliniccards", notes without a button, the failed-message retry. uk/ru/en. 390 px: no horizontal scroll, buttons 44 px. Screenshots: `docs/qa-screenshots/agent-booking/`.

**Tests.** `apps/api/test/agent-booking.spec.ts` (17): the whole path through the real services (fake model, transport, Cliniccards mock); a repeated yes, double click, parallel approval; "yes" to "find a time?"; unsent draft, old buttons, an offer older than a day; a taken place at the tap and after the consent; a changed time or service; no automatic booking in agent mode (also with `aiAutoBooking`) and the old behaviour with the agent off; unknown result of the card and of the visit (reads failing after the write), recheck, also when the visit occupies the only free cabinet; a Cliniccards refusal; visit created but message not delivered; an existing card without confirmed identity; isolation, roles, tampering; forged step without consent; memory without analytics; only-missing data and a linked patient.

**Limits.** The doctor-choice dialogue (named doctor, proposed doctor) is not a staff step yet: in agent mode its messages are held, the request goes to the administrator by hand. Rescheduling and cancelling are not part of the agent path. A "yes" typed as free text counts only for the question that was sent (a different phrasing goes to the staff). Cliniccards is the mock; no real visit or message was made. A step is stale after any new message of the patient (the staff member refreshes it). Per-process cache of the plan (a minute).

## 17. Stage 4: the limited autonomous mode (2026-11-05; local, fake model / transport / Cliniccards mock, no paid call, no real visit or message)

**What it is.** The same path as stage 3 (answer with times -> the patient's choice -> missing data -> the patient's consent -> the visit -> the confirmation) executed by the system without the staff buttons. No new booking logic: the steps are the same drafts, executed by `AgentApprovalService.approve(..., auto=true)` (same checks, same transport confirmation, same `BookingFlowService` / `BookingService.book`). The model still cannot choose BOOK.

**Switch and permission (`AgentAutoGate`).** All must hold, read again before every send and every visit: `aiAgentMode` AND `aiAgentAuto` (separate switch, off by default, set only by the service owner through `PATCH /platform/clinics/:id`; `aiAgentMode` alone never turns it on), sending on, not suspended, booking by cabinets, `agentAutoServiceId` = one approved service of the clinic (the only service whose times it may offer and book), the channel one of INSTAGRAM, MESSENGER, WHATSAPP, WEB, and the dialog in the SERVER variable `AGENT_AUTO_DIALOGS` (`<clinicId>|<CHANNEL>|<chatId>`, comma or space separated). A missing or empty list denies every dialog. Telegram goes through its own handlers and is not connected.

**Processing (`AgentAutoService`).** `IntakeService.handle` calls `onInbound` after the message is saved and the booking flow took its part (never throws). One dialog is processed by one worker: a lease on `ConversationState` (`leaseToken`, `leaseUntil`, 90 s, compare-and-set, renewed before each step); no database transaction is held over a model or channel call. A pass makes at most one send or one visit per step (max 6 steps), then looks again. A message that arrives while the lease is held is already saved; after letting go the holder checks for an unhandled last message (`autoSeenId`) and takes another round, so nothing is lost; a stale result (a new message arrived while the answer was prepared) is dropped and the dialogue is looked at again. A holder that stopped leaves an expired lease: the next message or the scheduler's `sweep()` over the listed dialogs takes over. An approval left half-way is settled as before (the channel's stored confirmation or UNKNOWN). Per step: a booking step of the open request first (the same `agentPlan`); otherwise one model draft whose action is executed if allowed (the answer, the times of the test service, a hand-over; a safe fallback hands over); anything else is left for a person.

**Right to act (`autoRight`, before the send and again right after the claim).** Permission still valid; the dialogue's `owner` is not HUMAN; the message the answer was prepared for is still the last one and nothing newer, no staff reply and no changed state exist (`staff_took_over` counts here, unlike for a staff member's own approval); no unfinished action (APPROVING or UNKNOWN draft, request `autoState` RUNNING or UNKNOWN); the service is the test service. For a visit also: the consent for the current key, a fresh placement, the write switches.

**Intervention.** A staff reply (or a staff-approved action) in a dialog of an autonomous clinic sets `owner=HUMAN`; the agent does nothing until the explicit return (`POST /conversations/:channel/:chatId/resume-bot` sets `owner=BOT` and looks at the unhandled message at once). The inbox shows "the dialogue is with a staff member". An unknown result of a send or a visit, a note step (identity not confirmed, urgent, no length, the time is gone, too many questions), an action not allowed in this mode, a failed send: the agent stops, one request for the staff is made (`HANDOFF`, they are told once), `owner=HUMAN`. Doctor choice, rescheduling and cancelling are not implemented here and stay a person's task.

**Fixed on the way.** The newest message of a dialogue is now chosen by (time, id) and "a message after the draft" is compared the same way: two messages saved in the same millisecond made the draft stale for ever (found by the quick-messages test). After an unknown result in the autonomous mode the check reuses the first attempt's place (also saved for the autonomous visit). The patient's automatic "message received" reply is not sent in agent mode.

**Tests.** `test/agent-auto.spec.ts` (12): the whole dialog without buttons; off by default, `aiAgentMode` alone, empty list, other dialog, not cabinets, no test service; repeated webhook and repeated yes (one visit); two quick messages (nothing lost, nothing duplicated); a staff reply during generation (nothing sent, owner HUMAN, an explicit return answers); the mode switched off before the send and before the visit; a stopped worker (live lease not taken over, expired lease taken over once) and an interrupted send (no resend, unknown, a person's task); a taken place; an unknown result of the visit (no repeat, then the staff recheck); an existing card without confirmed identity, BOOK proposed by the model, another service; isolation; same-millisecond messages. `funnel-events.spec.ts` covers the platform switch (owner only, the service must be an approved one of that clinic).

**Limits.** Real model, real channel and real Cliniccards are untested. Instagram/Messenger/WhatsApp/WEB only; booking by cabinets and one service only. The inbox shows who owns the dialogue but not the lease. A step is stale after any new message (the pass simply looks again). The per-chat daily AI reply cap (`aiRepliesPerChatDay`) limits the model turns.

## 20. Privacy of the booking contacts, a price asked in the middle of a booking, the name parsing (2026-11-06; local, no paid call)

**1. Contacts and the model (`apps/api/src/ai/contact-mask.ts`).** The name, the surname and the phone collected for the booking are processed by the code and stored in the request; the model does not need them. Every model call goes through `AiService.complete`, which now cleans a COPY before the request leaves (the stored chat and the request are unchanged; no other model is used for the cleaning): in the dialogue messages every recognisable phone (9-14 digits with the usual separators) and the contacts known for the chat (`contactsOf`: the request's names and phone, the linked card's name and phone, the name the channel gave), the names also with another case ending; in the system text only the known PHONES of the patient (the clinic's own phone is its approved fact and stays; names are not masked there because a stem of a patient's name can be a common word of the clinic's facts, as the working bot's test of the doctors' windows showed). The agent and the working bot build their dialogue through `scrubMessages`: the system's questions that collect the contacts and the patient's short answers to them are replaced by the notes `[запит даних для запису]` and `[дані для запису надіслано]`; every other message keeps its meaning with `[телефон]` / `[ім’я]`. The retry after a refused answer goes through the same call, so its reminder is cleaned as well. Example: «Мене звати Оксана Шевчук, мій номер +38 (097) 000-07-77, а скільки це коштує?» reaches the model as «Мене звати [ім’я] [ім’я], мій номер [телефон], а скільки це коштує?»; the summary the patient was shown («Дані для запису: Шевчук Оксана, 380970…») is a note for the model.
*Limits (not anonymisation):* a name or any detail the patient writes in free text and the application does not know as a contact (before the data question, a street, an employer, a diagnosis), a number in words or broken into pieces, the clinic's own numbers in its facts, staff names in the clinic's facts. `security.md` and `CLAUDE.md` say this exactly. Tests (`test/agent-privacy.spec.ts`): the unit rules, the ACTUAL body of the request to the provider (a fake provider at the fetch level, the real `LlmClient`), the request AND its repeat after a broken answer carry none of the synthetic name, surname and phone, the working bot's draft too, the stored chat keeps the original.

**2. A price asked in the middle of a booking.** `isPriceQuestion` now recognises "скільки це коштує", "сколько это стоит", "а яка ціна". A message that asks ONLY the price (`isPriceOnlyQuestion`, anchored, uk and ru) about the service of the dialogue (the request's service, else the service of the dialogue state) is answered by the code from the price list as it is now, with no model; the autonomous mode then asks the ONE pending step again (all the contact data if nothing was given yet). A mixed message ("сколько стоит и можно ли при беременности") is not taken: the classifiers and the model handle the rest by their own rules and a justified hand-over is not suppressed (a hand-over still ends the autonomous work).

**3. The name parsing.** The phone and the explicitly labelled name/surname are kept; two bare capitalised words ("Мене звати Оксана Шевчук, мій номер …") are kept as a PAIR and ONE short clarification is asked ("що з цього прізвище — «Оксана» чи «Шевчук»? Напишіть лише прізвище."; the answer must be one of the two words, anything else is asked again, a new pair replaces the old one); with the phone known and both names missing one question asks both ("Прізвище Коваль, ім’я Ірина"); one missing field is asked on its own; nothing already given is asked again. No model is used. The same rules serve the working scenario (the older tests were updated: two bare words now give one clarification instead of a separate surname question). In the agent path the consent question starts with the summary the patient confirms («Дані для запису: Шевчук Оксана, 380970…») and the consent key includes the contacts.
*Limits:* a name in lower case or with a patronymic is asked field by field; a correction of the data after the consent question is not parsed (the message goes to the model's turn).

**Corrections after the summary (2026-11-06).** After the summary of the contacts and the consent question a message that corrects a phone or a name, or says the data are wrong, is never a "yes" to the old summary (`BookingFlowService.agentCorrection`). What the code can take reliably is saved (a phone, labelled names, a name and a surname as a pair whose order is asked) and the new summary is asked only after the save; anything else ("це не мій номер", "не Оксана, а Олександра", "дані невірні", a lone name-like word) is NOT guessed: the request gets `autoNote=data_disputed`, the consent is cleared, the plan gives the note `data_wrong`, the autonomous mode makes one request for the staff, sets the owner HUMAN and says nothing about a correction. The consent key holds the contacts, and the consent buttons now carry the key of their question (`bookyes|<request>|<key>`, also in the Telegram handler): the button of an earlier question does nothing even after a new question is open; a tap that the flow did not take is not a free message for the model (it would have offered new times and wiped the booking). "Yes, the same phone again" stays a yes. Tests: `test/agent-auto.spec.ts`, group "виправлення даних після вопроса про підтвердження" (a phone, a name, "yes but the first name is …", two bare words, three unparseable phrasings, the old button after the correction, no visit by the old data).

**Known contacts in the system text.** The system prompt of the agent is built only from the clinic's name, its hours and public contacts, the approved reference (`KbService.factsFor`: services, prices, locations, answers) and the state lines written by the code (`послуга`, `час обрано`, counters, owner); the working bot's prompt adds `facts()` (counts of months, dates of visits). None of them reads the patient's name or phone, and the summary with the contacts exists only as an outgoing message of the dialogue (cleaned as a message). So no exclusion at assembly was needed; the known PHONES are still masked in the system text as a safety net, and the names are not (a stem of a name can be a common word of the clinic's facts).
