# Booking through the bot

One scenario for every channel (Instagram, Messenger, WhatsApp, Viber, web chat through `IntakeService`; Telegram through its own callback and message handlers). The code lives in `apps/api/src/automations/booking-flow.service.ts`; the state is kept on the `BookingRequest` row (one open request per chat), so it survives a restart.

## Steps
1. The person taps a time button: `onSlotChosen` saves the time, the service and the doctor on the open request (stage `COLLECT`). The staff is not notified yet.
2. If the name or the phone is missing (a linked card with both is enough), the bot asks for the missing part only. `onText` takes the answers (`parseContact`: a name needs two words and no question words; a phone is normalized). After 3 asks the request goes on with what it has. A typed phone never links the chat to an existing card.
3. `complete` (claimed once through stage `READY`): the summary is rebuilt with channel, name, phone, service, time and doctor, the staff is notified once ("Оновлення заявки"), then:
   - default mode: the client is told "Передали заявку ... Очікуйте підтвердження запису" (not that the booking is made);
   - automatic mode: `runAuto`.
4. The administrator presses "Внесено в Cliniccards" on a booking request: the form is prefilled from the visit found in Cliniccards (`GET /requests/:id/match`, a read) or from the chosen time; `POST /requests/:id/confirm` stores the actual data, marks the request done and sends the confirmation with the actual data. Nothing is written to Cliniccards. A repeat click returns `alreadyConfirmed` without sending.
5. Delivery state is on the request (`noticeStatus`: PENDING, SENT, FAILED, SKIPPED, with `noticeError`). The message row `bookconfirm:<requestId>` in `ChatMessage` is the claim, so there is one message per request. `POST /requests/:id/notice/retry` re-sends a FAILED or SKIPPED one; a PENDING one older than 5 minutes only with `force`. Channel limits are not bypassed (a closed reply window stays `window_closed`).

## Automatic mode
On only when all of these hold: the clinic's `aiAutoBooking`, the clinic's `bookingWriteEnabled`, the connector can write, and the service-wide `CLINICCARDS_WRITE_ENABLED=true` (the setting itself cannot be turned on without it; `bookingWriteSupported()` in `ai.service.ts`). It then:
- uses the linked card, or creates a new card only when no card has the phone (an existing card with the phone goes to the administrator: a phone alone is not proof);
- takes the visit length from the approved service in the knowledge base (default 30 minutes) and a free cabinet/doctor from the same schedule the offers came from;
- books through `BookingService.book` (fresh re-check of the place, one unique attempt key, read-back);
- a taken place: fresh times are offered as buttons and the request stays open; an unknown result (lost answer): the booking is checked once more before anything else; any other failure: the request goes to the administrator and the client is never told "you are booked";
- only after a successful answer is the client told, with the real time. The audit row `booking_request.confirmed` says `by: auto` or `by: admin`.

## The AI pause and why the AI can stay silent
- A person's answer in a chat pauses the AI for 30 minutes (`AutoReplyService.pausedUntil`). The thread shows "ШІ мовчить до ..." with a "Повернути боту" button (`POST /conversations/:channel/:chatId/resume-bot`, table `ChatBotResume`). Only messages with an author (a person) pause the AI; scripted messages of the booking flow and the booking confirmation have no author and `byAi: false`, so they neither pause the AI nor use up its daily allowance (6 model replies per chat per day).
- The booking flow takes a message only while it waits for a name or a phone, only when it really replies, not for a question (`?`) and not when the request is older than 6 hours.
- Every reason the AI did not answer is logged as a code (`AI autoreply skipped: <reason> (clinic <id>, <channel>)`): `clinic_suspended`, `ai_off`, `autoreply_off`, `sending_off`, `plan_without_autoreply`, `opted_out`, `paused_after_staff_reply`, `daily_ai_reply_cap`, `send_failed_*`. Flow side: `Booking flow did not take the message: stale|question`. No chat ids, texts, phones or tokens are logged.

## Dental words and sudden health problems
- `apps/api/src/ai/dental.ts`: the glossary the model gets (чистка, вісімка/восьмёрка, панорама/ОПТГ, приціл, КТ, нерв/канали, імплант, брекети...) and the search expansion for the clinic's reference (the patient says "чистка", the price list says "гігієна"). Services are still named only from the approved reference.
- A message with a sudden problem (acute pain, a swelling/флюс, bleeding, a broken tooth) and no question about medicines, a diagnosis, prices or a complaint never reaches the model: `ChatAssistantService.urgent` answers in code (no advice, no evaluation; "103 or 112" if the person feels very bad), offers the nearest free times as buttons and creates a request whose summary starts with "ТЕРМІНОВО" (the staff is told even when an open request exists). With no free times it is a hand-over marked urgent. Medicines, diagnosis, fever, prices and complaints still go straight to a person.

## Names, doctor and the confirmation (2026-11-03)
- The surname and the first name are never told apart by the order of words. A new person is asked for them all at once with labelled fields ("Прізвище Коваль, ім’я Ірина, телефон ..."), then one at a time (surname, first name, phone); an answer of two bare words is asked again. A person with a card is asked for nothing but a missing phone.
- The automatic mode asks "so, confirm?" (buttons or "так"/"ні") only when everything needed is known: a free place, the length of the service from the approved reference, and a doctor (the official API requires `doctor_id`). If a doctor is unknown (a clinic without doctor shifts) or the length is unknown, the request goes to an administrator and the client is not promised a booking. Details of the API requirements and the open assumptions: `cliniccards-api.md`, the section "Write requirements".
- Tests that read the free times through the mock API: `test/booking-auto-e2e.spec.ts` (nothing about the schedule is faked there).

## Choice of the doctor (2026-11-03)
Code: `apps/api/src/booking/` (`doctors.service.ts`, `availability.service.ts`, `doctor-choice.service.ts`), the settings card `apps/web/components/DoctorSettings.tsx`. Tests: `test/doctors.spec.ts`.
- **Data.** `Doctor` (the doctors read from Cliniccards `GET /staff`, role DOCTOR, by id; the services he provides as ids of the approved reference; whether he takes urgent patients), `DoctorAvailability` (the online-booking schedule kept in LANKA: weekly rows with a cabinet, and exceptions by date), `Clinic.primaryDoctorId/Name` (the doctor for a first booking). A request keeps `doctorId`, `doctorReason` (CLIENT_CHOICE, CONTINUATION, PRIMARY, SERVICE_MATCH, URGENT), `doctorState` and `urgent`; the reason is also in the audit (`booking_request.doctor`, `booking_request.confirmed`).
- **Order.** (0) A sudden health problem: only doctors marked as taking urgent patients, a priority request, never booked by the bot; a person who wanted a particular doctor is asked before another doctor is offered. If nobody is marked, the old urgent answer applies. (1) The patient's wish: the surname in any case is matched among the doctors of the clinic; an ambiguous surname is asked; only his times are shown; with no time or a service he does not provide, ANOTHER doctor is only proposed (yes/no), never swapped silently. (2) Continuation: only for a chat tied to a card, by the doctor who did the same service (plan items done by a doctor, visits that took place), not the last doctor; proposed first, times after the "yes"; several doctors in the history are asked. (3) The doctor for first visits: used only if he provides the service and has free time, otherwise a suitable doctor is proposed or a person takes the request. Not configured: the old behaviour.
- **Availability.** Shifts in Cliniccards, or the LANKA schedule, minus the visits of the doctor and of the cabinet and the reserved blocks. No shifts and no schedule means no schedule: nothing is offered and the request keeps the wished doctor for a person. Every write re-checks the place against fresh data of Cliniccards.
- **Automatic mode.** Needs a doctor from the list (so `doctor_id` is always a real id of Cliniccards), who provides the service (or treated the person with it), has a schedule and is free; the client confirms service, doctor, date and time in so many words; a changed doctor or time asks again. The settings show why a doctor cannot be booked by the bot.

## Booking by cabinets through one shared account (2026-11-03)
For clinics whose Cliniccards returns one common account instead of doctors (112 dental: "dental clinic 112"). A separate setting `Clinic.scheduleMode` (DOCTORS, the default, or CABINETS) from the way a request is handled: both the request for an administrator and the automatic booking work with both. It is never switched on by itself because the API returned one doctor.
- **Settings** (`/booking-settings`, the card "Як організовано розклад" and "Запис за кабінетами"): the shared account (a doctor that Cliniccards lists; its id is the `doctor_id` of the visit), the cabinets open for online booking (and which of them take urgent patients), the services allowed (approved, with a known length; optionally only in some cabinets), exceptions by date. The hours are the existing working hours of the clinic (`workHours`) plus the exceptions (`workHoursExceptions`); unset hours offer nothing. The settings list what is still missing (`no_shared_account`, `no_cabinets`, `no_services`, `no_hours`); the per-doctor demands (schedule and services of a doctor) do not apply in this mode.
- **Free times** (`cabinet-booking.service.ts`): per cabinet, the allowed hours minus EVERY visit in the cabinet whatever its doctor_id and the reserved blocks; the length of the service decides what fits. The visits and blocks are read from Cliniccards just before they are used (kept for a minute); when they cannot be read nothing is offered and nothing is confirmed. The write re-checks the cabinet against fresh data; `BookingService.book(..., sharedAccount: true)` skips the doctor-based conflict (the same doctor_id in another cabinet is not a conflict), the cabinet conflict stays.
- **Dialogue**: no doctor is chosen or shown; times only; "Конкретного лікаря призначає клініка"; the confirmation has "Лікар: Лікаря призначить клініка" and the note of the visit says the clinic assigns the doctor. A real doctor named by the patient is only a wish (`wishedDoctor`): the patient chooses "any doctor" (ordinary booking, the wish stays in the note) or "a wish for the administrator" (no time is promised). The history of the shared account is never read as a treating doctor. Urgent: only the cabinets allowed for urgent, one priority request, never booked by the bot. A button from before a change of the setting is dropped and new times are offered.
- **Open for a live test**: the official documentation says nothing about two visits with the same doctor_id at the same time in different cabinets. LANKA allows it in this mode; whether the real API accepts it must be checked with the owner before turning the mode on.
- Tests: `test/cabinet-booking.spec.ts`.

## Imported settings (2026-11-03)
`apps/api/src/integrations/settings-import.service.ts`: the working hours (GET `/schedule-settings`) and the price list (GET `/prices`) are read after every sync; the source and the time are kept (`Clinic.workHoursSource/UpdatedAt`, `priceListSyncedAt`) and shown. `GET /clinic/work-hours/info` says `configured: false` for hours never set; the readiness warnings (`no_hours`, `no_services`) are computed from what is saved. Tests: `test/settings-import.spec.ts`.

### Rules for the remaining import cases
- **Free windows report** never substitutes 09:00-20:00. Without doctor shifts and without saved hours it returns no rows and a `notice` (shown above the table); the waitlist and the chat assistant also get no times then.
- **Price: unknown vs 0.** `KbItem.priceUah` null = unknown, 0 = explicitly free (confirmable by the admin). A price of 0 in Cliniccards is read as "not set" for drafts (it never becomes the own price). A missing price alone does not block booking when the service is allowed and its length is known; the bot never promises a cost for an unknown price.
- **Vanished positions.** Only after a successful, complete read of the price list a previously imported position that is gone gets `missingInSourceAt`: new online bookings of it are paused (`service_missing_in_source`; the doctor choice and the flow placement pause too), history and existing requests stay. A sudden mass disappearance is treated as an incomplete answer (`note: suspicious_missing:<n>`) and nothing is marked. An error or a partial read never disables services. The admin decides: keep as own or switch off (`POST /knowledge/:id/missing`).
- **No linking by name.** A manual service is never linked to an imported one by title alone; `GET /knowledge/review` lists ambiguous matches, the admin links (`POST /knowledge/:id/link`) or dismisses (`/dismiss-match`).
- **Price discrepancy.** Only for a price the clinic set by hand on purpose (see "Imported services follow Cliniccards"): if the source now has another one, the bot names neither until the administrator accepts the source price or keeps the own one (`POST /knowledge/:id/price-source`).
- **Zero price from the source.** A 0 from Cliniccards is never "free" by itself: a draft keeps an unknown price until the administrator types 0 (that 0 stays through every sync; a draft only follows a positive source price). An approved item with an unknown price and a source price of 0 shows up in the review card, so "free" is always an explicit choice.
- **Old time button of a vanished service.** `onSlotChosen` stores nothing on the request and tells the client the service cannot be booked online for now; before an automatic visit `placement()` checks the service again from the database.

### Check after a deploy (owner, with the real 112 dental; read-only)
1. Run a sync (Integrations). Open Settings: the working hours card says "Cliniccards, updated <time>"; the booking settings card shows the price list count and time.
2. Compare the hours, the days off and holidays, and 3-5 services (name, group, price) with Cliniccards. Note services whose price is 0 in Cliniccards: they must show "price unknown".
3. In the booking settings give one service a length and a cabinet, approve it, allow it for online booking.
4. Knowledge page: look at the review card (price changes, vanished positions, ambiguous names) and decide each one.
5. Instagram scenario in the mode "request for the administrator" (automatic booking stays off): ask for that service, pick a time, give name and phone, see the request and press "Внесено в Cliniccards" only if the visit really exists.

## Prices in the chat (2026-11-04)
`KbService.factsFor` gives the model EVERY active service of the clinic (imported from Cliniccards, drafts included, or made by hand), whether or not it is allowed for online booking and whether or not it has a length. Doctors, addresses and answers still need approval.
- **A price is named only when known and current**: it follows the last read of the price list (`Clinic.priceListSyncedAt`, not older than 90 days) or was confirmed/edited by a person in the last 90 days. Unknown, a position that vanished from the price list, and a price the source and the clinic disagree about are given to the model as "price: do not name ... the administrator clarifies"; no old price, no zero. Allowed amounts for the check of the reply are exactly the known prices.
- **Every reply that names a price carries the notice** "Вартість попередня — точну суму та що входить у послугу уточнить адміністратор." (`withPriceNotice` in `guardrails.ts`, uk and ru, added by the code when the model forgot it). Replies with "від 1 500 грн" are rejected (`FROM_PRICE`), as are sums not in the clinic's list (so no sum of several positions).
- **A price question is not a hand-over** whenever the clinic has any service list (`pricesKnown`): the model answers, asks which service when several fit (the prompt forbids picking the cheapest), and for an unknown price says it is to be clarified without claiming that a request was passed on. Discounts, instalments, complaints and medical questions still go to a person; "пожалуйста" is no longer taken for a complaint.
- Tests: `test/kb.spec.ts`, section "прайс у переписці ШІ".

## Imported services follow Cliniccards (2026-11-04)
- Every position of the price list becomes a service by itself, already approved, with no approval of each one. A repeated import applies new names, descriptions, groups and prices without any decision of the administrator. The import never sets online booking, the length or the cabinets.
- **Local exceptions** are listed in `KbItem.localFields` (`title`, `text`, `priceUah`): a field the administrator edits by hand on an imported service (an edit equal to the source's value is no exception). An import never overwrites them; the free price 0 is kept the same way (a source 0 is "not set" and makes the own price unknown). "Accept the source price" returns the position to following Cliniccards.
- The migration `20261104200000_auto_price` moved the old state over: drafts imported earlier became approved services; a price that differed from the source, an explicit 0, a title that differed and the text of an approved position became local exceptions.
- **Who the AI trusts.** Services imported from the connected Cliniccards (active, not vanished from the price list) are used at once. A hand-made service is used only after approval; a hand-made draft is not published. Doctors, addresses and answers: approved only.
- **Search over the whole list.** With more than 40 services only the matches of the patient's words are put into the prompt, but the search runs over every position: Russian and Ukrainian spellings are folded together (`fold`/`stemsOf` in `ai/dental.ts`), synonyms are added (`expandForSearch`: чистка, пломба, удалить...), shorter stems are tried when nothing matched. With no match the prompt says that no match is not "no such service": no price, ask to clarify.
- **A sum belongs to its service.** `replyViolates(reply, allowed, { priced, service })` ties every sum named in the reply to the service named next to it (the best match by title words, then the whole reply, then the service the model reported): the price of another service of the same list is rejected, and so is a sum with no service named. The currency is checked (grn only). The unit of the price (per tooth etc.) is not checked by code: the model is told to name it only when the service text has it.
- Real-model check: `RUN_AI_EVAL=1 npx jest test/ai-eval.spec.ts -t "прайс у переписці"` (synthetic price list of 207 positions, no patient data, nothing is sent).
